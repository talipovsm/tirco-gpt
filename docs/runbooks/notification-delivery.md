# External notification outbox

`notify(tx, ...)` writes in-app notifications and one `NotificationDelivery` per enabled channel in the **same PostgreSQL transaction**. Only committed work is visible to the worker. The unique notification/channel pair prevents duplicate queue rows. Existing historical notifications are deliberately not backfilled or re-sent.

The production Node server polls `POST /api/system/jobs/notifications` every 30 seconds. Set `JOB_NOTIFICATION_INTERVAL_SEC=0` to disable the built-in poller, or set another positive interval (development defaults to disabled). External cron uses `Authorization: Bearer $CRON_SECRET`, like the existing secure-deal job. On multiple instances use a shared `CRON_SECRET`; set the actual `PORT` when starting on a non-default port. Serverless installations must use external cron. The two data modes are processed separately; DEMO deliveries are recorded as SKIPPED and never send to mirrored real email addresses.

Claims use PostgreSQL `FOR UPDATE SKIP LOCKED` and a 5-minute lease. Each claim increments attempts and assigns a random ownership token. A process restart loses no pending work; an expired claim is recovered on a later poll. A late worker cannot acknowledge a new owner's claim. SMTP attempts have bounded timeouts. Failures retry with exponential backoff starting at 30 seconds, capped at 6 hours; after 8 attempts status becomes FAILED. Delivery id is stable across retries and is passed as the SMTP Message-ID. Provider errors are not copied into queue records.

Delivery is **at least once**: SMTP can accept a message immediately before the worker crashes, so a retry can produce a duplicate. A stable Message-ID may help a mail provider deduplicate but is not an exactly-once guarantee. SENT means accepted by SMTP, not read or delivered into the inbox. `EMAIL_DRIVER=log` and demo-domain recipients produce SKIPPED, never SENT. Disabling an existing channel keeps queued work retryable; currently unimplemented Telegram/WhatsApp adapters do not enqueue deliveries. Password-reset/invitation direct emails are unchanged and are outside this business-notification outbox.

Deploy the additive migration to REAL and DEMO **before** deploying the new application. No existing objects or rows are rewritten; rollback the application first and leave the additive table in place. Check `NotificationDelivery` counts by status and age of the oldest due PENDING/PROCESSING row. Investigate FAILED rows and SMTP configuration/logs; once the cause is fixed, an operator can explicitly reset selected FAILED rows to PENDING with attempts=0, nextAttemptAt=now(), lockToken=NULL and lockedUntil=NULL. Do not reset SENT rows: this intentionally sends again.

Tests use fake adapters explicitly. `NODE_ENV=test` disables implicit real delivery; E2E should set `JOB_NOTIFICATION_INTERVAL_SEC=0` and `EMAIL_DRIVER=none`. Focused coverage: transaction rollback/commit visibility, competing workers, persistent retry, crash recovery, stale ownership, retry exhaustion and REAL/DEMO separation.
