# Резервное копирование, восстановление и выкат миграций

Runbook для OPS-05 из аудита. Контейнер при каждом старте применяет миграции к обеим базам (`scripts/docker-start.sh` → `scripts/db-modes.ts migrate`). Поэтому ошибочная миграция попадёт в production при деплое сама, без отдельного шага. Защита состоит из трёх частей: проверка миграций в CI, бэкап перед релизом с миграциями и проверенная процедура восстановления.

## Что хранится и где

| Данные                  | Где                                                              | Как копируется                                                                   |
| ----------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Реальная база           | `DATABASE_URL`, схема `public`                                   | бэкапы PostgreSQL на Railway + `pg_dump` перед релизом                           |
| Демо-база               | `DEMO_DATABASE_URL` или схема `tirco_demo` с меткой `tirco:demo` | не копируется: пересоздаётся `seed:demo`                                         |
| Файлы (документы, фото) | S3 (`STORAGE_DRIVER=s3`) или том контейнера                      | версионирование бакета S3; локальные файлы на томе без тома пропадают при деплое |

Демо-данные восстанавливать не нужно. Если демо-схема лежит в той же базе, она попадает в дамп вместе с реальной; это не мешает.

## Перед релизом, в котором есть новые миграции

1. CI зелёный, включая шаг `npm run db:check-migrations`. Он не пропускает изменённые или удалённые применённые миграции и разрушительный SQL без отметки ревью (см. ниже).
2. Проверьте, что на Railway включены и свежие автоматические бэкапы (Postgres → Backups). **Это нужно подтвердить владельцу**: из репозитория наличие бэкапов не видно.
3. Снимите ручной дамп непосредственно перед деплоем (с машины, у которой есть доступ к базе):

   ```sh
   pg_dump "$DATABASE_URL" --format=custom --no-owner --no-acl --file "tirco-$(date +%Y%m%d-%H%M).dump"
   ```

   Дамп содержит персональные данные: храните его в зашифрованном хранилище с ограниченным доступом и удаляйте по сроку.

4. Деплой. Миграции применятся при старте; в логах контейнера должно быть `✓ Обе базы в актуальном состоянии`.

## Правила для миграций

- Применённую миграцию **не редактируют и не удаляют** (в том числе `20261013210000_demo_email_domain_tirco`). Исправление делается новой миграцией. Контрольные суммы лежат в `prisma/migration-checksums.json`; новую миграцию после ревью добавляют командой `npm run db:check-migrations -- --write`.
- Разрушительные операции (`DROP TABLE/COLUMN/TYPE`, `TRUNCATE`, `DELETE`, `UPDATE`, смена типа колонки, `SET NOT NULL`, `RENAME`) выкатываются в два релиза: сначала код перестаёт использовать объект, затем миграция его удаляет. Такая миграция начинается строкой `-- migration-safety: reviewed — <план>`, где записаны бэкап, порядок выката и откат.
- Миграция должна применяться к обеим схемам (`public` и `tirco_demo`): объекты расширений указывайте с явной схемой (пример — `public.gin_trgm_ops` в `20261014140000_search_trigram_indexes`).
- Перед мержем миграция прогоняется на копии production-дампа (см. «Проверка восстановления»): так видно время выполнения и блокировки на реальном объёме.

## Восстановление

Порядок при неудачной миграции или потере данных:

1. Остановите приложение (Railway → сервис → Stop), чтобы новые записи не смешались с восстановленными.
2. Создайте новую базу (или используйте восстановление бэкапа Railway в новую базу). Не восстанавливайте поверх рабочей, пока не проверили копию.
3. Восстановите дамп:

   ```sh
   pg_restore --no-owner --no-acl --dbname "$NEW_DATABASE_URL" tirco-YYYYMMDD-HHMM.dump
   ```

4. Проверьте копию: число миграций в `_prisma_migrations`, количество пользователей, компаний и перевозок; метку демо-схемы `SELECT obj_description('tirco_demo'::regnamespace)` (должна быть `tirco:demo`, если демо-схема в той же базе).
5. Откатите код к версии, соответствующей дампу. Иначе старт контейнера снова применит проблемную миграцию.
6. Переключите `DATABASE_URL` на восстановленную базу и запустите сервис. Проверьте `/api/health` и вход.
7. Запишите инцидент: что потеряно между дампом и сбоем (журнал аудита, платежи провайдера), что сверено с провайдером платежей вручную.

## Проверка восстановления

Восстановление нужно периодически проверять на копии: бэкап, из которого не пробовали восстановиться, бэкапом не считается.

Проверка 14.10.2026 на локальной копии (PostgreSQL 16): `pg_dump --format=custom` базы с реальной и демо-схемой, затем `pg_restore` в новую базу. Совпали число пользователей (12), применённых миграций (13), грузов в демо-схеме (108) и метка `tirco:demo`. Проверка на дампе Railway остаётся за владельцем: из окружения разработки нет доступа к production.
