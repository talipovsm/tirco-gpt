## Как читать

**Приоритет** (по заданию аудита):

- **P0** — критическая уязвимость, потеря или повреждение данных, блокирующая ошибка;
- **P1** — важная ошибка бизнес-логики, доступа, ключевого сценария или надёжности;
- **P2** — существенная проблема UX/UI, технический долг, улучшение продукта;
- **P3** — необязательное улучшение, эксперимент, долгосрочная идея.

**Уверенность**:

- **подтверждено** — воспроизведено запросом/тестом/скриншотом или однозначно следует из кода (указано, чем именно);
- **вероятно** — механизм есть в коде, но последствия зависят от условий, которые не проверялись;
- **требует дополнительной проверки** — проверить в этом окружении нельзя (нет доступа к Railway, внешним сервисам и т. п.).

**Этап** — этап из [ROADMAP.md](ROADMAP.md), в котором предлагается исправление.

Номера строк указаны по коммиту `d63ee1f`.

## P0

### SEC-01 — Возможный администратор платформы с общеизвестным паролем в реальной базе Railway

- **Категория:** безопасность, эксплуатация. **Приоритет:** P0. **Уверенность:** требует дополнительной проверки (доступа к Railway в окружении аудита нет: прокси отвечает 403).
- **Описание.** 28.09.2026 стенд Railway настраивался на автоматический seed пустой production-базы: коммиты `40a0395` (11:24 UTC, «Prepare Railway demo deployment», `scripts/demo-seed-if-empty.mjs`), `7b9a5de` (12:29, «Allow demo seed on empty production database»), `1a1d07b` (13:48, «Re-run demo seed when the demo data is incomplete»). Общеизвестный пароль администратора убран из seed только в `43e865b` (15:27). Если стенд был засеян в этом окне, в реальной базе есть `admin@cargoflow.demo` с демо-паролем из README. Миграция `prisma/migrations/20261013210000_demo_email_domain_tirco/migration.sql:10` администраторов намеренно не переименовывает, а защита демо-стенда `sharedDemoAccount()` (`src/lib/auth/demo-stand.ts:16`) на администраторов не распространяется — вход в реальную базу для такого аккаунта открыт.
- **Реальный эффект (если подтвердится).** Любой посетитель демо-стенда получает права администратора платформы в реальной базе: все компании, пользователи, документы и перевозки; верификация компаний, блокировки, решения по спорам, настройки платформы, ручное подтверждение платёжных операций.
- **Рекомендуемое решение.** 1) Владельцу — проверить на Railway наличие `admin@cargoflow.demo` и других `PLATFORM_ADMIN` (запрос только на чтение) и попытку входа с демо-паролем; при успехе — сменить пароль или заблокировать аккаунт, отозвать его сессии, просмотреть журнал аудита за период. 2) В коде — проверка при старте production: если у активного `PLATFORM_ADMIN` хеш пароля совпадает с демо-паролем, писать `config.warning` и не допускать вход (или требовать смену пароля).
- **Зависимости:** OPS-01 (нужен штатный способ назначить нового администратора, если старого придётся заблокировать).
- **Риск исправления:** низкий; блокировка единственного администратора без OPS-01 оставит платформу без администрирования.
- **Критерии приёмки:** вход в реальную базу Railway с демо-паролем для любого `PLATFORM_ADMIN` невозможен; интеграционный тест: при production-конфигурации аккаунт администратора с демо-паролем не получает сессию; в журнале аудита зафиксированы действия по устранению.

### SEC-02 — API карточки груза раскрывает приватные заметки и контакты точек

- **Категория:** доступ к данным. **Приоритет:** P1. **Уверенность:** подтверждено (запросом в окружении аудита: перевозчик `carrier2@…` и экспедитор получили поля; HTML-страница эти поля не показывает).
- **Описание.** `getLoadDetail()` (`src/server/services/load.service.ts:366-421`) возвращает груз целиком (`prisma.load.findUniqueOrThrow` с `include`), включая `notes` (`prisma/schema.prisma:842`), `clientName` (`:818`) и у каждой точки `contactName`/`contactPhone`/`notes` (`:920-925`). Маршрут `GET /api/loads/:id` (`src/app/api/loads/[id]/route.ts:5`) отдаёт результат без фильтрации. Страница скрывает заметки от не-владельца (`src/app/(app)/loads/[id]/page.tsx:127`, подпись «Заметки (видны только вам)»), то есть интерфейс обещает приватность, которую API не обеспечивает. Доступ к карточке имеет любой перевозчик (опубликованный груз на бирже), экспедитор (роль `VIEWER`) и перевозчик, когда-либо сделавший ставку, — даже после выбора другого перевозчика (`src/server/services/access.ts:123-135`). Вне демо-стенда регистрация открыта и не требует проверки компании (см. SEC-04), значит получить роль перевозчика может кто угодно.
- **Реальный эффект.** Утечка внутренних заметок грузовладельца и персональных данных контактных лиц на погрузке/выгрузке всем перевозчикам платформы; возможность договориться напрямую в обход платформы; нарушение обещания интерфейса.
- **Рекомендуемое решение.** Ввести явные DTO по отношению к грузу: владелец/администратор — всё; перевозчик/экспедитор до сделки — без `notes`, `clientName` (если владелец не решит иначе), без `contactName`/`contactPhone` точек; выбранный перевозчик — контакты после подписания договора (или после принятия ставки — решение владельца продукта). Проверить тем же способом `GET /api/loads` (список), `/api/loads/:id/bids`, поиск, `next-load`, приложение водителя.
- **Зависимости:** решение владельца, когда перевозчику открываются контакты и видно ли имя клиента экспедитора.
- **Риск исправления:** средний — нативные приложения и страницы могут использовать эти поля; нужен поиск всех потребителей.
- **Критерии приёмки:** интеграционные тесты на состав ответа для ролей владелец / перевозчик без ставки / перевозчик со ставкой / выбранный перевозчик / экспедитор / водитель; поля `notes`, `contactName`, `contactPhone` отсутствуют там, где не положены; E2E «перевозчик открывает груз с биржи» проходит.

### OPS-01 — Нет штатного создания администратора платформы в production

- **Категория:** эксплуатация, бизнес-процессы. **Приоритет:** P1. **Уверенность:** подтверждено (код).
- **Описание.** `PLATFORM_ADMIN` создаётся только в `prisma/seed.ts:316`, а seed очищает базу (`TRUNCATE … CASCADE`, `:58-63`) и в production без `ALLOW_PRODUCTION_SEED=1` не запускается (`:273-274`). В production пароль администратора — из `DEMO_ADMIN_PASSWORD` или случайный, «доступ — через сброс пароля» (`:83-92`), но письма не отправляются (OPS-02). Других путей (скрипт, API, миграция) нет — проверено поиском по `src/`, `scripts/`, `prisma/`.
- **Реальный эффект.** На чистой production-базе нет администратора: не проходят верификация компаний, решение споров, снятие паузы, отмена перевозки после подписания договора (только администратор, см. BL-01), ручное подтверждение операций безопасной сделки (провайдер `manual` по умолчанию в production, `src/lib/payments/provider.ts:85-98`). Перевозки с открытым спором зависают навсегда.
- **Рекомендуемое решение.** Скрипт `admin:grant` (по образцу `scripts/ensure-demo-logins.ts`): назначает роль существующему пользователю или создаёт пользователя по email с паролем из переменной окружения; только реальная база; без `TRUNCATE`; запись в журнал аудита; явное подтверждение флагом. Описать в README и `docs/DATABASE_MODES.md`.
- **Зависимости:** нет. **Риск исправления:** низкий (изолированный скрипт), но это привилегированная операция — нужен тест и запрет на запуск без явного флага.
- **Критерии приёмки:** на пустой реальной базе скрипт создаёт администратора, другие таблицы не затронуты; повторный запуск идемпотентен; интеграционный тест; запуск против демо-схемы отклоняется.

### OPS-02 — Письма не отправляются: сброс пароля и приглашения не работают в production

- **Категория:** ключевой пользовательский сценарий. **Приоритет:** P1. **Уверенность:** подтверждено (код).
- **Описание.** `EmailNotificationAdapter` и `sendEmail()` (`src/lib/notifications/adapters.ts:38-51`, `:84-90`) только пишут письмо в лог; при любом `EMAIL_DRIVER`, кроме `log`, письмо «отключено». В production токены в тексте маскируются (`redactSecrets`), поэтому даже из логов ссылку не восстановить (это правильно). `requestPasswordReset()` (`src/server/services/auth.service.ts:289-310`) при этом отвечает «ok», а прежние неиспользованные токены аннулирует. Приглашения работают только через ссылку, которую приглашающий копирует из интерфейса.
- **Реальный эффект.** Пользователь, забывший пароль, не может восстановить доступ; страница «Восстановление пароля» обещает письмо, которое не придёт; email-уведомлений нет.
- **Рекомендуемое решение.** Реальный адаптер отправки (SMTP или HTTP API провайдера — выбрать и зафиксировать в ADR), повтор при ошибке, предупреждение при старте, если провайдер не настроен; до подключения — честный текст на странице восстановления («обратитесь к администратору компании/платформы»).
- **Зависимости:** выбор провайдера и домена отправителя (владелец), OPS-01 (администратор как запасной путь).
- **Риск исправления:** средний: новые секреты, доставляемость, утечка токенов в логи провайдера.
- **Критерии приёмки:** в staging с тестовым SMTP (например, Mailpit) E2E «забыл пароль → письмо → новый пароль → вход» проходит; без настроенного провайдера production пишет предупреждение при старте, а страница не обещает письмо; токены не попадают в логи.

- **Риск исправления:** средний — минорное обновление фреймворка может менять поведение кэша/прокси.
- **Критерии приёмки:** `npm audit --omit=dev` без high/critical; lint, typecheck, unit, integration, E2E, build — зелёные.

### SEC-04 — Регистрационный номер компании «занимается» без проверки

- **Категория:** бизнес-логика, злоупотребления. **Приоритет:** P1. **Уверенность:** подтверждено (код) — поведение; вероятно — злоупотребление.
- **Описание.** Уникальность `(country, registrationNumber)` проверяется при регистрации и при создании компании (`prisma/schema.prisma:645`, `src/server/services/auth.service.ts:79-94`, `src/server/services/company.service.ts:417-421`). Ни email, ни компания до этого не проверяются. Первый зарегистрировавшийся с чужим БИН/ИНН блокирует регистрацию настоящей компании («Компания с таким номером уже существует»).
- **Реальный эффект:** конкурент или мошенник может заблокировать вход компании на платформу; до верификации чужое название и номер видны контрагентам.
- **Рекомендуемое решение (требует решения владельца):** уникальность только среди `VERIFIED` компаний (частичный уникальный индекс) + очередь «спор о номере» для администратора; подтверждение email при регистрации; ограничение действий неверифицированной компании (уже частично есть — проверить).
- **Зависимости:** OPS-01 (администратор разбирает споры), OPS-02 (подтверждение email).
- **Риск исправления:** средний — изменение уникального ограничения требует миграции и проверки существующих данных на дубликаты.
- **Критерии приёмки:** вторая регистрация с тем же номером создаёт неверифицированную компанию; верификация второй при уже верифицированной первой отклоняется; миграция безопасна на копии production-данных.

### SEC-05 — Лимит входов в учётную запись считает успешные входы

- **Категория:** надёжность, доступность. **Приоритет:** P1. **Уверенность:** подтверждено (код).
- **Описание.** `enforceRateLimit("loginAccount", email)` вызывается до проверки пароля (`src/server/services/auth.service.ts:231`), лимит — 10 попыток за 15 минут (`src/lib/auth/rate-limit.ts:35`), счётчик не сбрасывается после успешного входа. На демо-стенде общие демо-аккаунты используют все посетители.
- **Реальный эффект:** на демо-стенде после 10 входов за 15 минут кнопка демо-доступа выдаёт «Слишком много попыток» всем посетителям; любой может заблокировать вход чужой учётной записи десятью неверными паролями.
- **Рекомендуемое решение:** считать только неудачные попытки; при успехе сбрасывать счётчик; для общих демо-аккаунтов на демо-стенде — без лимита на аккаунт (остаётся лимит по IP); рассмотреть прогрессивную задержку вместо жёсткой блокировки.
- **Зависимости:** нет. **Риск исправления:** низкий.
- **Критерии приёмки:** unit/integration-тесты: 20 успешных входов подряд проходят; 11-я неудачная попытка за окно отклоняется; лимит по IP сохраняется.

## P2

### BL-01 — После подписания договора стороны не могут отменить перевозку

- **Уверенность:** подтверждено (код). Начиная с `CONTRACT_SIGNED` переход в `CANCELLED` разрешён только администратору (`cancelByAdmin`, `src/lib/state-machine/order-state-machine.ts:90`, `:116` и далее); самостоятельная отмена — только в `CARRIER_SELECTED`/`CONTRACT_PENDING` (`SELF_CANCELLABLE_STATUSES`). Взаимной отмены по согласию сторон нет; спор и пауза тоже разрешаются только администратором.
- **Эффект:** любая отмена после подписания требует администратора (а его может не быть — OPS-01); стороны вынуждены открывать спор там, где конфликта нет.
- **Решение:** «отмена по соглашению сторон» до начала погрузки: одна сторона предлагает, другая подтверждает (с повторной аутентификацией, как при подписании), фиксация в истории и договоре; после погрузки — только спор/администратор.
- **Зависимости:** решение владельца; при безопасной сделке — возврат средств через `settleOnOrderCancel`.
- **Риск исправления:** средний (state machine, деньги). **Критерии приёмки:** тесты переходов; отмена без согласия второй стороны невозможна; при обеспеченной оплате запускается возврат.

### SEC-06 — Одна роль на всю компанию грузовладельца/экспедитора

- **Уверенность:** подтверждено (код). `ROLES_BY_COMPANY_TYPE` (`src/lib/permissions/index.ts:185`) даёт компаниям `SHIPPER`/`FORWARDER` единственную роль с полным набором прав (`CUSTOMER_PERMISSIONS`: подписание договоров, отмена, платежи, управление сотрудниками).
- **Эффект:** приглашённый менеджер может подписать договор, отменить перевозку, удалить коллег; невозможно разделить «оформляет заявки» и «подписывает/платит».
- **Решение:** роли `SHIPPER_ADMIN` / `SHIPPER_MANAGER` (по образцу `CARRIER_ADMIN`/`CARRIER_DISPATCHER`) с миграцией существующих участников в админов.
- **Риск исправления:** средний (миграция enum и данных, права во всех сервисах). **Критерии приёмки:** тесты RBAC для новой роли; существующие пользователи сохраняют доступ.

### DATA-01 — Файлы реальной и демо-базы лежат вместе

- **Уверенность:** подтверждено (код). Ключ файла — `${scope}/${год}/${месяц}/${uuid}` (`src/lib/storage/storage.ts:108`) без признака режима данных; сброс/пересев демо-схемы файлы не удаляет.
- **Эффект:** анонимные загрузки на демо-стенде копятся в том же бакете, что и реальные документы; их нельзя выборочно удалить или настроить им отдельную политику хранения.
- **Решение:** префикс `real/` / `demo/` для новых файлов; задача очистки демо-файлов; отдельный бакет для демо — по решению владельца.
- **Риск исправления:** низкий для новых файлов; перенос старых — отдельная операция с бэкапом. **Критерии приёмки:** новые файлы получают префикс режима; очистка демо не трогает `real/`.

### OPS-05 — Миграции при старте контейнера без шага резервного копирования

### OPS-07 — Публичные тайлы OpenStreetMap в production

- **Уверенность:** подтверждено (код). Без `NEXT_PUBLIC_MAP_STYLE_URL`/`NEXT_PUBLIC_GEOAPIFY_KEY` карта грузит `tile.openstreetmap.org` (`src/features/tracking/map-style.ts:9`, `:25`), комментарий сам называет это вариантом для dev.
- **Эффект:** нарушение политики использования тайлов OSM при росте нагрузки, нет SLA; в окружении аудита карты были пустыми (сеть закрыта) — интерфейс при этом не сообщает об ошибке загрузки карты.
- **Решение:** в production требовать провайдера карт (предупреждение при старте, как для `APP_URL`); показывать «карта недоступна» при ошибке тайлов. **Критерии приёмки:** предупреждение при старте без ключа; заглушка при недоступной карте.

### PERF-01 — Опрос чата пишет в БД

- **Уверенность:** подтверждено (код); влияние на нагрузку требует нагрузочного теста. Чтение сообщений делает `chatThread.upsert` и `chatReadState.upsert` (`src/server/services/chat.service.ts:13`, `:63`), клиент опрашивает каждые 5 с; `unreadMessagesTotal()` (`:178-182`, до 500 перевозок) вызывается на каждом рендере `(app)/layout.tsx:9` и `driver/layout.tsx:15`.

### UX-01 — Недостаточный контраст текста

- **Уверенность:** подтверждено (axe-core на 48 экранах, 1440×900 и 390×844, светлая и тёмная тема). 369 узлов `color-contrast` (serious). Основные причины:
  - `text-tertiary-foreground` используется для содержимого (коды стран KZ/UZ рядом с городами, подсказка `Ctrl K`): 3,26:1 (светлая), 3,69:1 (тёмная) при 11 px — по `docs/design-system.md` этот токен только для плейсхолдеров и неактивного;
  - `text-muted-foreground` на серых заливках (сайдбар, `fill-quaternary`, сегменты): 4,29–4,41:1 при 11 px — заявленные в дизайн-системе 5,1:1 верны только на белом;
  - тёмная тема, подпись на бегунке сегмента: 2,62:1.
- **Решение:** заменить `tertiary` на `muted` для содержимого; затемнить `muted-foreground` для серых поверхностей (или отдельный токен «вторичный текст на заливке»); проверить пары в обеих темах. Подробно — [UX_UI_RECOMMENDATIONS.md](UX_UI_RECOMMENDATIONS.md#1-доступность-и-контраст).
- **Критерии приёмки:** axe `color-contrast` — 0 нарушений на ключевых экранах в обеих темах; автоматическая проверка в E2E.

### SEC-07 — Администраторы без иерархии

Подтверждено (код): `adminSetUserStatus()` (`src/server/services/admin.service.ts:164`) запрещает блокировать только самого себя; другого администратора заблокировать можно; назначения/снятия роли платформы в интерфейсе нет. Решение: запрет блокировки последнего активного администратора, журнал смены ролей (вместе с OPS-01). Критерий: тест «нельзя заблокировать последнего администратора».

### SEC-08 — Произвольный текст на странице «Нет доступа»

Подтверждено (код): `src/app/forbidden/page.tsx:14-27` выводит `?reason=` из ссылки, отсекая URL, `@` и номера из 7+ цифр; текст вида «Ваш аккаунт взломан, срочно смените пароль» проходит. Решение: принимать только коды причин из белого списка. Критерий: неизвестный код показывает стандартный текст.

### SEC-09 — Вебхуки: подпись без метки времени по умолчанию

Подтверждено (код): `src/lib/payments/provider.ts:134-149` — формат без метки времени принимается, пока не задан `WEBHOOK_REQUIRE_TIMESTAMP=1`; явного лимита размера тела у сырых маршрутов (`/api/payments/webhooks/[provider]`, `/api/integrations/*`) нет. Повторы смягчаются идемпотентной обработкой. Решение: в production требовать метку времени по умолчанию; ограничить размер тела. Критерий: тест — запрос без метки времени в production отклоняется.

### SEC-10 — Госномер уникален на всю платформу

Подтверждено: `prisma/migrations/20260928120000_audit_integrity/migration.sql:151` — `UNIQUE (country, plateNumber) WHERE deletedAt IS NULL`. Компания может внести чужой номер и заблокировать его добавление владельцем. Решение: процедура оспаривания у администратора или уникальность в пределах компании + предупреждение. Требует решения владельца.

### BL-03 — Проверка обеспечения оплаты вне транзакции

Подтверждено (код): `src/server/services/order.service.ts:250-261` проверяет безопасную сделку перед `AT_LOADING` до транзакции перехода. Критерий: тест параллельных «отменить сделку» и «начать загрузку».

### BL-05 — «Доставлено» без документов

## Проверенные и не подтвердившиеся риски

Для полноты — гипотезы, которые проверялись и **не** подтвердились:

- **IDOR между компаниями** (подтверждено запросами от имени посторонней компании-перевозчика, водителя, диспетчера и грузовладельца): чужая перевозка, её чат, скачивание документа, PDF договора — 403; изменение чужой машины и чтение чужого уведомления — 404; изменение участника чужой компании — 403; рейс другого водителя — 403; админ-API для обычного пользователя — 403; топливный счёт для диспетчера — 403. Водитель видит свой рейс без суммы сделки (`agreedAmount: null`), платежи и договор рейса — 403. Публичный профиль чужой компании открыт намеренно и содержит только публичные поля. Скачивание документа чужой компании не проверено (в тестовых данных не было таких документов).
- **CSRF:** изменяющие запросы с чужим `Origin` отклоняются (`src/lib/api/handler.ts`, проверено запросом — 403); cookie сессии `HttpOnly`, `SameSite=Lax`.
- **Повторная отправка и гонки:** двойное принятие ставки, параллельные ставки, повтор смены статуса, пересечение рейсов водителя — покрыты интеграционными тестами (`tests/integration/security-and-rules.test.ts:144-279`), блокировки `SELECT … FOR UPDATE` в переходах статусов.
- **Подмена файлов:** проверка сигнатуры содержимого и размера (`src/lib/storage/file-validation.ts`), тест подмены содержимого есть.
- **Секреты в репозитории:** не найдены (проверены `.env*`, конфиги, скрипты, workflow; демо-пароль публичен намеренно).
- **Самоназначение привилегий:** схема регистрации не содержит роли платформы (`src/lib/validation/auth.ts:51-70`, только тип деятельности), смена роли участника проверяет допустимость для типа компании, запрещает менять свои права и права основателя, оставляет хотя бы одного руководителя (`src/server/services/company.service.ts:253-273`); права вычисляются на сервере (`src/lib/permissions/index.ts`).
- **Демо-данные в реальной базе:** `seed:demo` отказывается работать против реальной схемы, полный seed — в production (тесты в `tests/integration/data-modes.test.ts`).
