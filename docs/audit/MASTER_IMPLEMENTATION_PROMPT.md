# Мастер-промпт: последовательное улучшение TIRCO

> Скопируйте текст ниже в Claude Code, открытый в корне репозитория `tslaprojects/tirco`. Укажите в конце, какой этап или задачу выполнять (по умолчанию — следующую невыполненную задачу этапа A). Промпт составлен по аудиту версии 0.3.0 (коммит `d63ee1f`, 13.10.2026): `docs/audit/`.

---

Ты работаешь с существующим проектом **TIRCO** — платформой для международных грузоперевозок (грузы, биржа и торги, перевозки по этапам, договор с подписью внутри платформы, документы, трекинг, споры, безопасная сделка через платёжного провайдера, следующий рейс, топливный контроль, админка, нативные приложения на Flutter). Твоя задача — **улучшать его небольшими последовательными шагами** по результатам аудита, не переписывая приложение и не ломая существующие сценарии.

## 0. Перед началом любой задачи

1. Прочитай `CLAUDE.md` и `AGENTS.md`. Это **Next.js 16** с изменёнными API: перед кодом, затрагивающим Next.js, читай соответствующий раздел в `node_modules/next/dist/docs/` и учитывай предупреждения об устаревании. Вместо middleware — `src/proxy.ts`; фоновые задачи стартуют из `src/instrumentation.ts`.
2. Прочитай документы аудита: `docs/audit/BUGS_AND_RISKS.md` (ID находок), `docs/audit/BUSINESS_LOGIC.md` (процессы и права), `docs/audit/ROADMAP.md` (этапы), для интерфейса — `docs/audit/UX_UI_RECOMMENDATIONS.md` и `docs/design-system.md`. Режимы данных — `docs/DATABASE_MODES.md`.
3. Для любой задачи по интерфейсу используй skill `ui-ux-pro-max` (`--stack nextjs`, `--stack shadcn`; для `--design-system` — `--density 7-9 --motion 1-3`). Направление дизайна выбрано: **«Системное приложение»** (развитие текущего), без смены палитры и шрифтов.
4. Найди в коде все места, которые затронет изменение (вызовы, импорты, маршруты, нативные клиенты в `native/`), прежде чем менять.

## 1. Архитектура, которую нужно сохранить

- **Маршруты API** — `src/app/api/**/route.ts`, все через обёртку `route()` (`src/lib/api/handler.ts`): проверка `Origin`, сессия и режим данных, лимиты частоты, идемпотентность по заголовку `Idempotency-Key`, проверка UUID, единый JSON-ответ и русские сообщения ошибок. Сырые маршруты (вебхуки, системные задачи) проверяют подпись/секрет сами. Новые маршруты — только через `route()`.
- **Бизнес-логика** — в `src/server/services/*.service.ts`; права проверяются в сервисах (`src/lib/permissions/index.ts`, `src/server/services/access.ts`), интерфейс лишь скрывает недоступное. Не переносить проверки в клиент.
- **Машины состояний** — `src/lib/state-machine/order-state-machine.ts` и `payment-state-machine.ts`; переходы перевозки — только через `performTransitionInTx` (блокировка строки, ожидаемый исходный статус, история). Статусы денег безопасной сделки меняет только результат провайдера (`PROVIDER`).
- **Режимы данных REAL/DEMO** — `src/lib/db/data-mode.ts`, `src/lib/db/prisma.ts`: `prisma` маршрутизируется по режиму сессии, `authDb` — всегда реальная база. Демо-стенд = `NODE_ENV=production` и `DEMO_SEED=1` (`src/lib/auth/demo-stand.ts`).
- **Хранилище файлов** — `src/lib/storage/storage.ts` (локально или S3), проверка файлов — `src/lib/storage/file-validation.ts`.
- **Уведомления** — `src/server/services/notification.service.ts`, внешние каналы — `src/lib/notifications/adapters.ts`.
- **Платежи** — интерфейс `PaymentProvider` (`src/lib/payments/provider.ts`): `sandbox` / `manual`. Деньги хранит только лицензированный провайдер.
- **Интерфейс** — только русский; сохраняй `data-testid` (их используют E2E), реестр `StatusBadge`, общие компоненты `src/components/common`; токены — `src/app/globals.css`.
- **Тесты** — `tests/unit`, `tests/integration` (реальный PostgreSQL), `tests/e2e` (Playwright). Команды: `npm run lint`, `npm run typecheck`, `npm run format:check`, `npm run test:unit`, `npm run test:integration`, `npm run test:e2e`, `npm run build`.

## 2. Неизменные правила

1. **Не переписывай с нуля** и не дублируй существующие возможности: сначала найди, что уже есть (копирование груза — `republishLoadCopy`, подбор — `src/lib/next-load/matching.ts`, приглашения — `CompanyInvite`, уведомления, DTO и т. д.).
2. **Никаких заглушек под видом функций.** Если функция не подключена к реальному источнику (почта, платёжный провайдер, телематика), интерфейс должен честно это говорить; демо-данные помечаются «DEMO». Не пиши «сделано», если сценарий не проверен.
3. **Опасные операции с данными запрещены**: не запускай `npm run db:reset`, `prisma migrate reset`, `npm run db:seed`, `npm run db:purge-demo`, `seed:demo:reset`, `TRUNCATE`/`DROP` ни против чего, кроме одноразовой локальной базы, которую ты сам создал для тестов. Не подключайся к production-базе. **Не редактируй применённые миграции** (в том числе `prisma/migrations/20261013210000_demo_email_domain_tirco`) — только новые миграции. Миграция должна быть аддитивной или иметь план отката и проверку на дубликаты/конфликты существующих данных.
4. **Секреты** не копируй в код, логи, тесты, документы и PR; новые переменные окружения — в `.env.example` с безопасным примером и в README.
5. **Зависимости**: новая библиотека — только если задачу нельзя разумно решить существующими средствами; обоснование — в ADR. Не обновляй мажорные версии попутно.
6. **Архитектурные решения** (провайдер почты, правила регистрации, DTO, роли заказчика, отмена по соглашению, хранение журналов) — коротким ADR в `docs/adr/NNNN-название.md`: контекст → решение → альтернативы → последствия.
7. **Визуальные задачи не меняют бизнес-логику, API и права**; бизнес-задачи не смешиваются с редизайном.
8. Каждый PR — одна задача из плана, ссылка на ID находки (например, `SEC-02`), описание изменений, результаты проверок (реальный вывод, а не «должно работать»), что не проверено и почему.
9. Если задача требует решения владельца продукта (список в разделе 6) — остановись и задай вопрос с вариантами и рекомендацией, не принимай продуктовое решение молча.

## 3. Протокол выполнения каждой задачи

1. **Понять**: прочитать код и тесты затрагиваемой области; сформулировать в 3–5 строках, что меняется и что не должно измениться.
2. **Зафиксировать ошибку тестом**: написать регрессионный тест (unit или integration, для UI — E2E), убедиться, что он падает на текущем коде.
3. **Исправить минимально**: самое маленькое изменение, которое закрывает находку; без попутного рефакторинга.
4. **Проверить**: `npm run lint`, `npm run typecheck`, `npm run format:check`, `npm run test:unit`, `npm run test:integration`, `npm run test:e2e`, `npm run build`. Для интерфейса — скриншоты 1440 px и 390 px в светлой и тёмной теме, axe на изменённых экранах.
5. **Перечитать дифф как ревьюер**: права и изоляция компаний, режимы REAL/DEMO, идемпотентность и гонки, утечки полей в ответах, русские тексты, `data-testid`.
6. **Обновить документацию**: README/`docs/*`, ADR при архитектурном решении, отметить статус находки в `docs/audit/BUGS_AND_RISKS.md` (исправлено в PR №…).
7. **Отчитаться**: что сделано, какие проверки запускались и с каким результатом, что не проверено.

После завершения **каждого этапа** — полный прогон всех проверок; найденные регрессии исправляются до перехода к следующему этапу.

### Этап D — новые логистические возможности

Каждую функцию начинай с короткого описания проблемы, роли, метрики успеха (из `docs/audit/PRODUCT_IDEAS.md`) и подтверждения от владельца. Порядок: «Создать по образцу» (переиспользовать `republishLoadCopy`) → резервный перевозчик → «Мои перевозчики» и приглашение партнёра в груз → онбординг → подписки на грузы → Next Load 2.0 (фоновый расчёт, маршрутизатор с кэшем) → репутация по исполнению → изменение условий после подписания → уровни доверия → сроки документов машин → иерархия администраторов. Исследование платёжного провайдера — документом, без кода. Приёмка: функция работает на реальных данных, есть тесты правил и прав, применены DTO из A1.1, метрика измеряется.

### Этап E — подготовка к росту

Сначала: runbook бэкапа и восстановления с проверкой на копии, правило ревью миграций (OPS-05); трекер ошибок с маскировкой ПДн и оповещения о неуспешных фоновых задачах (OPS-06). Затем нагрузочный тест (биржа, дашборд перевозчика, чат, поиск на объёме ×100 от демо-данных) и **только по его результатам**: чат без записей при опросе (PERF-01), фоновый подбор следующего рейса (PERF-02), `pg_trgm` и keyset-пагинация (PERF-03), одна загрузка сессии на запрос (PERF-04). Политика хранения журналов (DATA-02) — до подключения телематики; общее хранилище лимитов и блокировка задач (PERF-05) — только при переходе на несколько инстансов; обязательная метка времени в вебхуках (SEC-09) — до подключения реальных провайдеров.

## 5. Проверки, которые нельзя пропускать

- Изоляция компаний: запрос к чужому объекту по подменённому id → 403/404 (интеграционный тест на каждый новый endpoint).
- Режимы данных: новые операции записи не пишут в реальную базу из демо-сессии (`tests/integration/data-modes.test.ts` — расширять).
- Гонки и повторы: новые изменяющие операции — с `idempotency` в `route()` и блокировкой строки при переходах.
- Состав ответа: новые API возвращают только положенные роли поля.
- Интерфейс: только русский текст, `data-testid` сохранены, axe без новых нарушений, нет горизонтальной прокрутки на 360 px.
- Миграции: `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code` (как в CI) и применение на копии данных.
