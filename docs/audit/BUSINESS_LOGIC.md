# Бизнес-логика TIRCO: фактические процессы и состояния

Восстановлено по коду, схеме базы и тестам версии 0.3.0 (коммит `d63ee1f`). Документация проекта использовалась как подсказка, но каждое утверждение ниже сверено с кодом. Ссылки на проблемы — ID из [BUGS_AND_RISKS.md](BUGS_AND_RISKS.md).

## 1. Участники и права

### 1.1. Модель

- **Пользователь** (`User`) — учётная запись; роль платформы `USER` или `PLATFORM_ADMIN`; статус `ACTIVE`/`BLOCKED`.
- **Компания** (`Company`) типа `SHIPPER` (грузовладелец), `CARRIER` (перевозчик), `FORWARDER` (экспедитор); статус проверки `UNVERIFIED → PENDING → VERIFIED / REJECTED / SUSPENDED`.
- **Членство** (`Membership`) связывает пользователя с компанией и ролью: `SHIPPER`, `FORWARDER`, `CARRIER_ADMIN`, `CARRIER_DISPATCHER`, `DRIVER`. Допустимые роли по типу компании — `src/lib/permissions/index.ts:185`.
- Пользователь может состоять в нескольких компаниях и переключать активную (`POST /api/auth/switch-company`).
- Права — фиксированные наборы на роль (`ROLE_PERMISSIONS`, `src/lib/permissions/index.ts:151`), администратор платформы получает все права. Источник истины — сервисы на сервере; интерфейс только скрывает недоступные действия.

### 1.3. Проблемы прав

- **SEC-06 (P2).** У грузовладельца и экспедитора одна роль на всю компанию: любой приглашённый сотрудник подписывает договоры, отменяет перевозки, ведёт платежи и управляет коллегами. У перевозчика разделение есть (`CARRIER_ADMIN` / `CARRIER_DISPATCHER`).
- **SEC-02 (P1).** Право «смотреть биржу» на уровне API открывает перевозчикам и экспедиторам приватные поля груза (заметки, контакты точек, имя клиента экспедитора); перевозчик, когда-то сделавший ставку, сохраняет доступ к карточке после выбора другого исполнителя (`src/server/services/access.ts:123-135`).
- **Экспедитор не может работать как перевозчик-посредник:** у роли `FORWARDER` нет `BID_CREATE` — экспедитор только размещает грузы от имени клиентов и смотрит биржу. Если бизнес-модель предполагает перепродажу перевозки, это ограничение надо снять отдельным решением.
- **SEC-07 (P3).** Администраторы равноправны, может быть заблокирован последний активный администратор (запрещено только блокировать себя).

## 2. Компания: регистрация, приглашения, проверка

**Как работает.** Регистрация (`POST /api/auth/register`, `src/server/services/auth.service.ts`) создаёт пользователя и либо новую компанию выбранного типа (роль-основатель), либо присоединяет по приглашению. Приглашение (`CompanyInvite`, статусы `PENDING/ACCEPTED/REVOKED/EXPIRED`) — токен в ссылке, хранится хеш. Проверка компании: владелец загружает документы (`CompanyDocument`) и отправляет заявку (`VerificationRequest`: `PENDING → APPROVED / REJECTED / CHANGES_REQUESTED`), решение принимает администратор (`adminCompanyDecision`). На демо-стенде регистрация закрыта.

**Проблемы.**

- **SEC-04 (P1).** Уникальность регистрационного номера проверяется до любой проверки — номер можно «занять».
- **OPS-02 (P1).** Нет подтверждения email и нет доставки писем: приглашение передаётся только ссылкой вручную.
- **OPS-01 (P1).** Без администратора проверка компаний невозможна.

## 3. Груз (`Load`)

### 3.1. Состояния

`DRAFT → PUBLISHED → BIDDING → CARRIER_SELECTED → CONVERTED_TO_ORDER`, из `DRAFT/PUBLISHED/BIDDING` — `CANCELLED`.

| Переход                                 | Кто                       | Условия и последствия                                                                                                  | Код                                      |
| --------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| создание → `DRAFT`                      | грузовладелец, экспедитор | мастер из 4 шагов (маршрут, груз, транспорт, цена); у каждой точки местное время; можно опубликовать сразу             | `load.service.ts:121` `createLoad`       |
| `DRAFT → PUBLISHED`                     | владелец                  | видимость `MARKETPLACE` или `INVITE_ONLY` (приглашённые перевозчики); ограничения публикации по типу груза — настройка | `load.service.ts:243-274`, `publishLoad` |
| `PUBLISHED → BIDDING`                   | система                   | первая ставка                                                                                                          | `bid.service.ts:128`                     |
| `BIDDING → PUBLISHED`                   | система                   | все ставки отозваны/отклонены                                                                                          | `bid.service.ts:313`, `:353`             |
| `BIDDING → CARRIER_SELECTED`            | владелец                  | принятие ставки; остальные `PENDING` → `REJECTED`; создаётся перевозка                                                 | `bid.service.ts:379-484` `acceptBid`     |
| `CARRIER_SELECTED → CONVERTED_TO_ORDER` | система                   | подписан договор                                                                                                       | `contract.service.ts:280`                |
| `→ CANCELLED`                           | владелец                  | только из `DRAFT/PUBLISHED/BIDDING`; ожидающие ставки → `REJECTED`                                                     | `load.service.ts:311-356` `cancelLoad`   |
| `CARRIER_SELECTED → CANCELLED`          | система                   | отмена перевозки до подписания                                                                                         | `order.service.ts:324`                   |

Редактировать можно черновик и опубликованный груз без ставок (после правки опубликованный груз снова проходит проверки публикации). При наличии ставок (`BIDDING`) изменение запрещено: «Отмените груз и создайте новый» (`load.service.ts:173-175`) — участники торгов при этом теряют свои ставки; аккуратное изменение условий с уведомлением участников — кандидат в улучшения этапа B.

### 3.2. Наблюдения

- **Отказ перевозчика до подписания** создаёт копию груза: опубликованную, если дата погрузки ещё актуальна, иначе черновик (`order.service.ts:352-410`). Остальные ставки исходного груза при принятии были отклонены, поэтому прежние участники торгов о повторной публикации не узнают — заказчик начинает торги заново. Идея «резервного перевозчика» — в [PRODUCT_IDEAS.md](PRODUCT_IDEAS.md).
- **Отмена заказчиком до подписания** отменяет и груз — повторной публикации нет (это решение заказчика).
- **Вопросы по грузу** видны всем, если на них ответили; неотвеченные — только задавшей компании.
- **SEC-02 (P1).** Приватные поля груза уходят в API всем, кто видит карточку.

## 4. Ставка (`Bid`)

Состояния: `PENDING → ACCEPTED / REJECTED / WITHDRAWN / EXPIRED`. Переписка по ставке — `BidMessage` (`OFFER / COUNTER / COMMENT / ACCEPTED / REJECTED / WITHDRAWN`).

| Действие              | Кто        | Правила                                                                                                 | Код                               |
| --------------------- | ---------- | ------------------------------------------------------------------------------------------------------- | --------------------------------- |
| Сделать ставку        | перевозчик | одна активная ставка компании на груз (проверка в транзакции); груз опубликован и виден                 | `bid.service.ts:61-128`           |
| Встречное предложение | заказчик   | по `PENDING`-ставке                                                                                     | `bid.service.ts:178` `counterBid` |
| Ответ на встречное    | перевозчик | принять/отклонить/своё предложение                                                                      | `bid.service.ts:227`              |
| Отозвать              | перевозчик | только `PENDING`                                                                                        | `bid.service.ts:297`              |
| Отклонить             | заказчик   | с причиной                                                                                              | `bid.service.ts:330`              |
| Принять               | заказчик   | груз не выбран; ставка не истекла; сумма/валюта совпадают с ожидаемыми (защита от смены цены «на лету») | `bid.service.ts:379-484`          |
| Истечение             | система    | `validUntil < now` → `EXPIRED` при чтении (`expireStaleBids`), не фоновой задачей                       | `bid.service.ts:37-40`            |

**Конкурентность** (покрыто тестами `tests/integration/security-and-rules.test.ts:144-242`): одновременное принятие двух ставок создаёт одну перевозку; двойной клик не создаёт дублей (идемпотентность + блокировки); параллельные ставки одного перевозчика — одна активная; отозванную и просроченную ставку принять нельзя.

## 5. Перевозка (`TransportOrder`)

### 5.1. Машина состояний

Единственный источник правил — `src/lib/state-machine/order-state-machine.ts`; переход выполняет `performTransitionInTx` с блокировкой строки (`SELECT … FOR UPDATE`), проверкой ожидаемого исходного статуса и записью истории.

```
CARRIER_SELECTED → CONTRACT_PENDING → CONTRACT_SIGNED → VEHICLE_ASSIGNED → DRIVER_ASSIGNED → WAITING_FOR_LOADING
→ AT_LOADING → LOADED → IN_TRANSIT ⇄ (AT_BORDER → CUSTOMS → BORDER_CLEARED → IN_TRANSIT) → AT_DELIVERY → DELIVERED → CLOSED
Из большинства активных: → DISPUTED (спор), → ON_HOLD (пауза, только админ), → CANCELLED
```

| Группа переходов                                        | Кто                                            | Через что                                                                  |
| ------------------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------------------- |
| `CARRIER_SELECTED → CONTRACT_PENDING → CONTRACT_SIGNED` | система                                        | создание договора и подписи обеих сторон                                   |
| назначение/снятие машины и водителя                     | перевозчик, админ                              | `POST/DELETE /api/orders/:id/vehicle`, `/driver`; до `WAITING_FOR_LOADING` |
| этапы рейса (`AT_LOADING` … `AT_DELIVERY`)              | водитель, перевозчик, админ                    | `POST /api/orders/:id/status` с подтверждением, вложениями, координатами   |
| `AT_DELIVERY → DELIVERED`                               | водитель, перевозчик, админ                    | отдельная операция `POST /api/orders/:id/deliver` (фото/POD — по желанию)  |
| `DELIVERED → CLOSED`                                    | заказчик, админ; система при безопасной сделке | `POST /api/orders/:id/confirm-delivery`                                    |
| отмена до подписания                                    | заказчик, перевозчик, админ                    | `POST /api/orders/:id/cancel` с причиной                                   |
| отмена после подписания                                 | только админ                                   | там же                                                                     |
| спор                                                    | заказчик, перевозчик, админ                    | `POST /api/orders/:id/dispute`                                             |
| пауза и возврат из спора/паузы                          | только админ                                   | `POST /api/admin/orders/:id/hold`, `PATCH /api/disputes/:id`               |

Ресурсы: машина и водитель считаются занятыми в статусах `RESOURCE_BUSY_STATUSES`; пересекающиеся рейсы водителя запрещены (тест «водитель занят на пересекающемся рейсе»). Снять машину/водителя можно до `WAITING_FOR_LOADING` включительно.

### 5.2. Согласованность груза и перевозки

- Перевозка создаётся только принятием ставки, в той же транзакции груз → `CARRIER_SELECTED`; один груз — одна перевозка.
- Отмена перевозки отменяет черновые договоры, плановые платежи и груз; при обеспеченной оплате запускается возврат через провайдера (`settleOnOrderCancel`).
- Отменённая/закрытая перевозка — финальные статусы без исходящих переходов; проверка исходного статуса в транзакции не даёт «продолжить» отменённую перевозку.

### 5.3. Проблемы

- **BL-01 (P2).** После подписания договора стороны не могут отменить перевозку по взаимному согласию — только администратор. Вместе с **OPS-01** это тупик на чистой production-базе.
- **BL-03 (P3).** Условие «оплата обеспечена» перед `AT_LOADING` проверяется вне транзакции перехода (`order.service.ts:250-261`).
- **BL-05 (P3).** «Доставлено» можно отметить без документов; POD требуется только при закрытии.
- **BL-04 (P3).** Недостижимые значения `DRAFT/PUBLISHED/CARRIER_SELECTION` в `OrderStatus`.
- **BL-06 (P3).** Срок подтверждения в уведомлении — всегда время Алматы.

## 6. Договор (`Contract`)

- Создаётся системой из шаблона (`ContractTemplate`, код + версия) сразу при принятии ставки (`createContractInTx`, вызов в `bid.service.ts:513`; реализация — `contract.service.ts:51`); у документа есть хеш содержимого.
- Статусы: `DRAFT → PENDING_SIGNATURES → PARTIALLY_SIGNED → SIGNED`, `CANCELLED` при отмене перевозки.
- Подпись (`signContract`, `contract.service.ts:190-300`): только уполномоченные представители сторон; повторный ввод пароля; клиент передаёт хеш просмотренной версии — подпись отклоняется, если документ изменился после открытия или хеш не совпадает; метод подписи — `INTERNAL_ACCEPTANCE` (простое электронное согласие внутри платформы, не КЭП/ЭЦП).
- После второй подписи: перевозка → `CONTRACT_SIGNED`, груз → `CONVERTED_TO_ORDER`.
- PDF генерируется по запросу (`pdf-lib`, `GET /api/contracts/:id/pdf`); каждый просмотр пишется в журнал аудита.

Ограничение: юридическая сила «внутреннего согласия» зависит от юрисдикции и пользовательского соглашения — это вопрос к юристам, не к коду. Квалифицированной электронной подписи нет (идея — в [PRODUCT_IDEAS.md](PRODUCT_IDEAS.md), раздел «не сейчас»).

## 7. Документы перевозки (`OrderDocument`)

- Типы: договор, заявка, CMR, инвойс, упаковочный лист, документы машины и водителя, фото груза и пломбы, POD, прочее.
- Загрузка (`POST /api/orders/:id/documents`): проверка размера и сигнатуры содержимого, лимит частоты; новая версия того же типа помечает старую `SUPERSEDED`; удаление — мягкое (`DELETED`), после доставки POD/CMR удалить нельзя (`document.service.ts:179`).
- Скачивание — только участникам перевозки с правом `DOCUMENT_VIEW`; каждое скачивание пишется в журнал аудита.
- Хранилище: локальная папка или S3-совместимое (`src/lib/storage/storage.ts`); ключи без признака режима данных — **DATA-01 (P2)**.

## 8. Трекинг и уведомления

- Водитель отправляет координаты и отметки этапов (`POST /api/orders/:id/tracking`, `/status`), источник — веб или приложение водителя; GPS-провайдеров нет (поле `GPS_PROVIDER` в enum зарезервировано).
- Уведомления (`Notification`, 23 типа) создаются в транзакциях бизнес-операций; каналы: в приложении — работает; email — только лог (**OPS-02**); Telegram и WhatsApp — точки расширения, сообщения не отправляют (`src/lib/notifications/adapters.ts:54-75`).
- Чат перевозки (`ChatThread`, опрос раз в 5 с) — **PERF-01 (P2)**: чтение пишет в БД.

## 9. Подтверждение доставки и закрытие

`confirmDelivery()` (`order.service.ts:807-860`):

1. только заказчик или админ, только из `DELIVERED`;
2. если включено `requirePodForClose` — нужен активный POD или CMR;
3. при обеспеченной безопасной сделке — запускается выплата перевозчику, перевозка закроется после подтверждения провайдером;
4. при необеспеченной сделке — сделка отменяется, расчёты переходят в ручной учёт;
5. перевозка → `CLOSED`, создаётся плановый платёж на непогашенный остаток.

Окно подтверждения при безопасной сделке — `confirmationWindowHours` (по умолчанию 72 ч); по истечении фоновая задача (`processConfirmationTimeouts`, раз в 10 минут в production через `src/instrumentation.ts` → `POST /api/system/jobs/secure-deal`) запускает выплату перевозчику, если есть POD/CMR и нет открытого спора; без документов перевозка пропускается с причиной «Нет подтверждающих документов». Та же задача повторяет зависшие операции провайдера и выполняет обслуживание (`runMaintenance`).

## 10. Расчёты

### 10.1. Ручной учёт (`PaymentRecord`: `PREPAYMENT / FINAL_PAYMENT / OTHER`)

Статусы `PLANNED → INVOICED → PAID / CANCELLED`. Сумма платежей не может превышать стоимость перевозки, валюта — валюта сделки (тест «сумма платежей не может превышать стоимость»). Это учёт, а не движение денег.

### 10.2. Безопасная сделка (`PaymentRecord` типа `SECURE_DEAL`)

Принцип в коде: «Tirco не хранит и не перемещает деньги», статусы денег меняет только результат операции провайдера (`src/lib/state-machine/payment-state-machine.ts`).

```
PAYMENT_PENDING → (PAYMENT_AUTHORIZED) → PAYMENT_RESERVED → PAYMENT_RELEASE_PENDING → PAYMENT_RELEASED
                                              ↘ PAYMENT_DISPUTED ↗          ↘ PAYMENT_PARTIALLY_RELEASED
финальные: PAYMENT_RELEASED, PAYMENT_REFUNDED, PAYMENT_FAILED, PAYMENT_CANCELLED
```

- Переходы в `RESERVED/RELEASED/REFUNDED` — только `PROVIDER`; ни один HTTP-endpoint не принимает «целевой статус».
- Операции (`PaymentTransaction`: `AUTHORIZE/RESERVE/RELEASE/REFUND/VOID`) идемпотентны, зависшие операции повторяются фоновой задачей (`retryStaleOperations`).
- Провайдеры: `sandbox` (операции успешны сразу; в production запрещён, кроме демо-стенда) и `manual` (по умолчанию в production: каждую операцию подтверждает администратор) — `src/lib/payments/provider.ts:85-98`. **Интеграции с реальным лицензированным провайдером нет** — функция реализована как каркас и ручной режим.
- Вебхуки провайдера: HMAC-подпись, по умолчанию допускается формат без метки времени — **SEC-09 (P3)**.
- Комиссия платформы рассчитывается (`src/lib/payments/commission.ts`); условия выплаты — `release-conditions.ts`.
- Настройка «оплата обязательна до загрузки» (`requireSecureDeal`) блокирует `AT_LOADING` без обеспеченной оплаты (покрыто тестом).

## 11. Споры (`Dispute`)

- Открыть: заказчик или перевозчик из любого активного статуса после выбора перевозчика (`DISPUTABLE_STATUSES`), причина из справочника (`NOT_DELIVERED`, `DELAY`, `DAMAGE` …). Перевозка → `DISPUTED`, обеспеченная оплата замораживается (`freezeForDispute`), администраторы получают уведомление.
- Комментарии сторон и администратора; статусы `OPEN → IN_REVIEW → RESOLVED / REJECTED`.
- Решение — только администратор: вернуть перевозку в прежний статус, закрыть или отменить; по деньгам — выплатить, вернуть или разделить (`validateDisputePaymentOutcome`, `settleDisputeOutcome`).
- Без администратора (**OPS-01**) спор не разрешается никогда; сроков рассмотрения и эскалации нет.

## 12. Отзывы и рейтинг

После закрытия перевозки (`CLOSED`, `review.service.ts:15`) каждая сторона может оставить отзыв (`POST /api/orders/:id/review`, идемпотентно); рейтинг компании — среднее по отзывам (`companyRatings`). Отзыв показывается в профиле компании и на карточке груза.

## 13. Следующий рейс (Next Load)

- Перевозчик или водитель указывает намерение после доставки (`MovementIntent`: `RETURN` — домой, `CITY` — в город, `DIRECTION` — в направлении, `UNDECIDED`), регион и сроки (`POST /api/next-load/movements`).
- Подбор (`src/lib/next-load/matching.ts`): кандидаты — до 500 опубликованных грузов (`next-load.service.ts:190`); предпросмотр на дашборде перевозчика.
- Результат — рекомендации; ставку делает человек. Расстояния и пустой пробег оцениваются по прямой с коэффициентом извилистости (`src/lib/geo/distance.ts`, комментарий в `matching.ts:17`), маршрутизация провайдером используется только в превью маршрута груза. Проверяются грузоподъёмность и совместимость кузова; сортировки — эффективность, расстояние до погрузки, отклонение, ставка, дата.
- **PERF-02 (P3)**: подбор выполняется при каждом рендере дашборда.

## 14. Топливо (Fleet Fuel Control)

- Топливный счёт компании (`FuelAccountEntry`: пополнение, резерв, списание, возврат, корректировка), топливные карты с лимитами и статусами, привязка к водителю/машине.
- Транзакции заправки (`FuelTransaction`: `PENDING → AUTHORIZED → APPROVED → COMPLETED`, также `DECLINED/REVERSED/REFUNDED/DISPUTED`) из источников `PROVIDER/MANUAL/DRIVER_APP/DEMO`.
- Сопоставление с телематикой (уровень топлива, GPS) → статус проверки (`MATCHED/PARTIALLY_VERIFIED/UNVERIFIED/MISMATCH`) и аномалии по правилам (`src/lib/fuel/anomaly-rules.ts`: место не совпадает с GPS, уровень не соответствует, превышение объёма бака, падение уровня, частые заправки, отклонение от маршрута).
- Расследования с комментариями и вложениями; формулировка в интерфейсе корректная: «несоответствие — сигнал для проверки, а не вывод о нарушении».
- Реальные процессинговые центры и телематика не подключены: есть демо-провайдер, приём вебхуков с HMAC (`/api/integrations/fuel-cards/[provider]/webhook`, `/api/integrations/telematics/[provider]/ingest`) и симулятор АЗС. В интерфейсе это честно помечено «DEMO DATA».

## 15. Администрирование

Админка (`/admin/**`, доступ — `PLATFORM_ADMIN`, `src/app/admin/layout.tsx:9`): обзор, перевозки, грузы, споры, безопасные сделки (операции, «обработать истёкшие сроки»), верификация, документы, топливные проверки, пользователи (блокировка), компании (решение по проверке), журнал аудита, настройки платформы (безопасная сделка, окно подтверждения, POD при закрытии, ограничения публикации). Покрытие тестами `admin.service` — 0 % (**QA-01**).

## 16. История действий

`AuditLog` пишется сервисами в той же транзакции, что и изменение (вход, создание/изменение объектов, переходы, подписи, просмотры договоров, скачивания документов, денежные операции). `TransportOrderStatusHistory` хранит переходы перевозки с источником и вложениями, `PaymentStatusHistory` — переходы платежей. Срок хранения не задан — **DATA-02 (P3)**.
