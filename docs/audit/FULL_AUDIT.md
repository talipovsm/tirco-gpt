## 0. Коротко

**Как устроен TIRCO.** Монолит на Next.js 16 (App Router, React 19, TypeScript) с PostgreSQL 16 через Prisma 7: 50 страниц, 124 API-маршрута через единую обёртку `route()`, 34 сервиса с бизнес-логикой, 51 модель и 56 перечислений в схеме, 9 миграций. Две базы в одном PostgreSQL — реальная и демо (отдельная схема), режим выбирается при входе. Процессы: груз → торги → перевозка → договор с подписью внутри платформы → назначение машины и водителя → рейс по этапам с трекингом и документами → подтверждение получения → закрытие и отзывы; споры решает администратор; безопасная сделка — машина состояний поверх платёжного провайдера (в production по умолчанию ручной режим); «следующий рейс» и топливный контроль; нативные приложения на Flutter. Развёрнут на Railway как демо-стенд.

**Что в хорошем состоянии.** Изоляция данных между компаниями (все проверки подменой id — 403/404), CSRF-защита, транзакции с блокировками и идемпотентность (покрыты тестами гонок), машины состояний перевозки и платежей, хеш и повторная аутентификация при подписании договора, проверка содержимого файлов, отсутствие секретов в репозитории, честная маркировка демо-функций, единая дизайн-система и продуманные состояния интерфейса. Все локальные проверки зелёные: lint, typecheck, format, unit 159/159, integration 140/140, E2E 8/8, build.

**Самое опасное.**

1. **SEC-01 (P0, требует проверки):** в реальной базе Railway может существовать администратор платформы эпохи CargoFlow с общеизвестным паролем — по истории git стенд засевался до того, как пароль убрали из seed.
2. **SEC-02 (P1, подтверждено):** `GET /api/loads/:id` отдаёт любому перевозчику и экспедитору приватные заметки владельца и контакты на погрузке/выгрузке, хотя интерфейс обещает «видны только вам».
3. **OPS-01 / OPS-02 (P1, подтверждено):** в production нельзя штатно создать администратора и не отправляются письма — проверка компаний, споры, отмена подписанных перевозок и восстановление пароля упираются в тупик.
4. **SEC-03 (P1):** `next@16.3.6` с известными уязвимостями (исправлено в 16.4.0).
5. **SEC-04, SEC-05 (P1):** регистрационный номер компании можно «занять» без проверки; лимит входов блокирует общие демо-аккаунты и позволяет блокировать чужой вход.

**Что делать первым:** этап A [плана](ROADMAP.md) — сначала владелец проверяет SEC-01 на Railway (минуты, только чтение), затем DTO груза, обновление Next.js, лимит входов, E2E в CI, создание администратора и почта. Обоснование — в конце документа.

## 2. Как устроен TIRCO

### 2.1. Стек и размер

- **Веб:** Next.js 16.3.6 (App Router, RSC, `src/proxy.ts` вместо middleware, `src/instrumentation.ts` для фоновых задач), React 19.2, TypeScript, Tailwind 4, Radix UI, zod 4, react-hook-form, maplibre-gl (динамический импорт), pdf-lib, sonner, AWS S3 SDK. 400 файлов `.ts/.tsx`, ≈ 41 тыс. строк; 24 зависимости и 15 dev-зависимостей.
- **Данные:** Prisma 7.10 с `@prisma/adapter-pg`, PostgreSQL 16; 51 модель, 56 перечислений, 9 миграций; 6 частичных уникальных индексов и 35 CHECK-ограничений в миграциях; номера `CF-L/CF-O/CF-C` из последовательностей.
- **Нативные приложения:** Flutter, `native/apps/tirco` и `native/apps/driver` + общий пакет `native/packages/tirco_core` (42 файла `.dart`); у приложения водителя есть очередь отправки без сети (`native/apps/driver/lib/services/outbox.dart`); вход по токену покрыт интеграционными тестами.
- **CI:** `.github/workflows/ci.yml` (lint, typecheck, format, unit, integration на PostgreSQL, дрейф миграций, build), `native.yml` (сборка приложений).
- **Развёртывание:** `Dockerfile` + `scripts/docker-start.sh` (миграции обеих схем → на демо-стенде демо-аккаунты и фоновый seed демо-схемы → `next start`), Railway.

### 2.2. Слои

```
src/app/(auth|app)/…/page.tsx, src/app/admin, src/app/driver   — страницы (RSC), layout-guard по роли
src/app/api/**/route.ts → route() (src/lib/api/handler.ts)      — Origin, сессия и режим данных, лимиты, идемпотентность, ошибки
src/server/services/*.service.ts                                — бизнес-логика, права, транзакции, аудит, уведомления

src/features/**, src/components/{common,layout,ui}              — интерфейс
```

### 2.3. Режимы данных REAL / DEMO

Одна база PostgreSQL, демо-данные — в отдельной схеме с меткой (`tirco:demo`); `prisma` — прокси, выбирающий клиент по режиму сессии (AsyncLocalStorage + область рендера), `authDb` (пользователи, сессии) — всегда реальная схема. Демо-стенд = `NODE_ENV=production` и `DEMO_SEED=1`: регистрация закрыта, общие демо-аккаунты входят только в демо-базу, их старые сессии в реальной базе недействительны (tslaprojects/tirco#4). Защиты от ошибок: `seed:demo` отказывается работать с реальной схемой, полный `seed` (с `TRUNCATE`) не запускается в production без `ALLOW_PRODUCTION_SEED=1`, миграции применяются к обеим схемам. Подробно — `docs/DATABASE_MODES.md`.

## 3. Frontend

- **Страницы:** 50 (`page.tsx`): публичные (главная, вход, регистрация, восстановление, приглашение), кабинет `(app)` для заказчиков и перевозчиков, `/driver/**` для водителя, `/admin/**`, `/forbidden`. Опись с назначением, доступом, данными, действиями и проблемами — [UX_UI_RECOMMENDATIONS.md §2](UX_UI_RECOMMENDATIONS.md#2-опись-страниц).
- **Данные:** страницы — серверные компоненты, вызывающие сервисы напрямую; изменения — через `api()` (`src/lib/client/api.ts`) с ключом идемпотентности, обработкой сети и истёкшей сессии; после действий — обновление маршрута. Кэширования ответов на клиенте нет (и не нужно при текущей модели).
- **Компоненты:** доменные папки `src/features/*`, общие — `src/components/common` (EmptyState, ErrorState, скелетоны, DataTable, SplitView, StatusBadge…), 63 клиентских компонента. Крупные клиентские модули: `fuel-actions.tsx` (847 строк), `order-actions.tsx` (842), `load-wizard.tsx` (625) — кандидаты на разбиение при следующей правке, не отдельной задачей.
- **Формы:** react-hook-form + zod (те же схемы, что на сервере), ошибки полей с сервера.
- **Асинхронность и утечки:** опрос чата раз в 5 с с паузой на скрытой вкладке и очисткой таймера; карта подгружается динамически. Утечек и ошибок рендеринга в проверке не найдено (консоль — только сетевые ошибки тайлов).
- **Бизнес-логика на клиенте:** нет — права и правила только на сервере, клиент лишь скрывает действия.
- **Проблемы:** UX-01…UX-08, OPS-07 — см. BUGS_AND_RISKS.

## 4. Backend и API

### 4.1. Общее поведение всех маршрутов

`route()` (`src/lib/api/handler.ts`): сессия обязательна по умолчанию (`auth: false` — только вход, регистрация, восстановление, выход, health); проверка `Origin` для изменяющих запросов; режим данных из сессии до первого запроса к базе; лимиты частоты по профилям (`critical`, `upload`, `chat`, `routePreview`); идемпотентность по заголовку `Idempotency-Key` с резервированием ключа до выполнения (повтор с тем же ключом получает сохранённый ответ, параллельный повтор отклоняется, зависшая резервация снимается через 5 минут); проверка UUID в параметрах; единый JSON `{ success, data | error: { code, message, fields } }` с русскими сообщениями; неожиданные ошибки — 500 без деталей наружу, с логом. Сырые маршруты (вебхуки платежей, топливных карт, телематики, системные задачи) проверяют HMAC-подпись или `CRON_SECRET` (сравнение без утечки по времени).

### 4.2. Валидация

Все изменяющие маршруты либо разбирают тело схемой zod (`parseJson(req, schema)`), либо не принимают тела (действия: опубликовать, отозвать, отменить сделку, прочитать уведомление), либо проверяют форму загрузки вручную (файл обязателен, комментарий обрезается). Отсутствующей серверной валидации не найдено.

### 4.4. Ошибки и транзакции

Бизнес-ошибки — `AppError` с кодами (`INVALID_STATE_TRANSITION`, `DUPLICATE_ACTION`, `CONTRACT_ALREADY_SIGNED`, `RATE_LIMITED`…); изменения связанных объектов, аудит и уведомления — в одной транзакции; переходы — с `SELECT … FOR UPDATE`. Исключения: проверка обеспеченной оплаты перед погрузкой вне транзакции (BL-03); `settleOnOrderCancel` после транзакции отмены (операция провайдера идемпотентна и повторяется задачей). Неэффективные запросы — PERF-01…04.

## 5. Бизнес-логика

Подробно — [BUSINESS_LOGIC.md](BUSINESS_LOGIC.md). Главные выводы:

- Машины состояний перевозки и платежа централизованы, недопустимые переходы отклоняются, финальные статусы не имеют выходов, повторы и гонки защищены блокировками и идемпотентностью — подтверждено тестами.
- Согласованность «груз ↔ перевозка ↔ договор ↔ платежи» обеспечена транзакциями и уникальными ограничениями (одна перевозка на груз, одна принятая ставка, одна активная подпись компании, один открытый спор).

## 6. База данных и хранение

- **Модели и связи** соответствуют процессам; внешние ключи добавлены миграцией целостности `20260928120000_audit_integrity` (с предварительной очисткой висячих ссылок).
- **Ограничения:** 6 частичных уникальных индексов (одна активная ставка перевозчика, одна принятая ставка на груз, одна активная подпись компании, один активный документ в группе версий, один открытый спор, уникальный госномер среди неудалённых машин) и 35 CHECK (положительные суммы и веса, порядок дат, диапазоны комиссий, баланс топливного счёта ≥ 0, формат последних цифр карты…).
- **Удаление:** мягкое для пользователей, грузов, машин, документов (`deletedAt`/статус); каскад — для подчинённых записей (28 связей `onDelete: Cascade`).
- **История:** `AuditLog`, `TransportOrderStatusHistory`, `PaymentStatusHistory`, история ставок; срок хранения не задан (DATA-02).
- **Индексы:** по статусам, компаниям, датам и сочетаниям для фоновых задач; нет индексов под `ILIKE '%…%'` (PERF-03).
- **Миграции:** 9, проверка дрейфа схемы в CI; последняя (`20261013210000_demo_email_domain_tirco`) применена на Railway — менять её нельзя. Миграции применяются автоматически при старте контейнера (OPS-05).
- **Неправильная база / демо в production / опасная миграция:** защищено от запуска seed против реальной схемы и полного seed в production; риск остаётся в автоматическом применении миграций без бэкапа (OPS-05) и в ручных командах `db:reset`, `db:purge-demo` — они запрещены мастер-промптом вне одноразовой локальной базы.
- **БД и файловое хранилище:** в базе — метаданные документов (имя, тип, размер, хеш, ключ), сами файлы — в локальной папке или S3; разделения по режимам данных нет (DATA-01).
- **Бэкапы:** механизмов и процедуры в репозитории нет; наличие на Railway требует проверки.

## 7. Безопасность

Сильные стороны: изоляция компаний и ролей на уровне сервисов (проверено запросами), CSRF по `Origin` + `SameSite=Lax`, `HttpOnly`-cookie, CSP, HSTS, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy` (`next.config.ts:22-41`), хеши токенов сессий и приглашений, повторная аутентификация при подписании, единый ответ при восстановлении пароля (не раскрывает существование email), маскирование email и токенов в логах production, проверка сигнатуры файлов, HMAC у вебхуков и `CRON_SECRET` у задач, IP клиента — из доверенного прокси (`TRUSTED_PROXY_HOPS`), запрет sandbox-платежей в production. SQL-инъекций не найдено: запросы через Prisma; сырой SQL в сервисах — только параметризованные шаблоны `$queryRaw` (блокировки строк `FOR UPDATE`, агрегаты чата); `$queryRawUnsafe` — только для `nextval` по имени последовательности из константы (`src/lib/numbering.ts:13`), `$executeRawUnsafe` — только в seed. XSS: React экранирует вывод, `dangerouslySetInnerHTML` с пользовательскими данными не найден.

Находки: SEC-01 (P0, требует проверки), SEC-02…SEC-05 (P1), SEC-06 (P2), SEC-07…SEC-10 (P3) — [BUGS_AND_RISKS.md](BUGS_AND_RISKS.md).

## 10. Производительность и масштабирование

OPS-01/OPS-02 блокируют ключевые процессы production (администрирование, споры, отмена подписанных перевозок, восстановление доступа).
