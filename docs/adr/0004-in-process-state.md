# 0004. Лимитер частоты и планировщик — в памяти процесса

**Контекст.** Аудит (PERF-05): лимитер частоты (`src/lib/auth/rate-limit.ts`), планировщик плановой задачи (`src/instrumentation-node.ts`), подавление повторных оповещений (`src/lib/alerting.ts`) и суточный интервал чистки по срокам хранения (`src/server/services/maintenance.service.ts`) хранят состояние в памяти процесса. При нескольких инстансах лимиты делятся на число инстансов, а задачи запускаются в каждом из них.

**Решение.** Пока приложение работает одним инстансом (Railway, один сервис), состояние остаётся в памяти. Внешнее хранилище (Redis) не добавляется: оно усложняет эксплуатацию и ничего не даёт при одном процессе.

Корректность при росте обеспечена заранее:

- плановые задачи идемпотентны: выплаты и операции провайдера защищены ключами идемпотентности и блокировками строк, а повторный запуск обслуживания ничего не ломает;
- лимитер реализует интерфейс `RateLimiter`, поэтому реализацию на Redis можно подставить без изменения вызывающего кода;
- внешний cron (`POST /api/system/jobs/secure-deal` с `CRON_SECRET`) заменяет встроенный планировщик, если выключить его через `JOB_SECURE_DEAL_INTERVAL_MIN=0`.

**Когда пересмотреть.** Перед запуском второго инстанса нужно:

1. перенести лимитер в Redis;
2. выключить встроенный планировщик и вызывать задачу внешним cron;
3. принять, что подавление повторных оповещений работает в каждом инстансе отдельно (допустимо).

**Альтернативы.** Хранить счётчики лимитера в PostgreSQL. Отклонено: каждая попытка входа добавляет запись в базу, а при атаке перебором нагрузка ложится на основную базу.
